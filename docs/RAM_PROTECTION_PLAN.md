# План: захист від нестачі оперативної пам'яті (mgOS)

**Статус:** тільки план, нічого не змінено. 2026-11-15.
**Мета:** коли RAM закінчується (важка гра, багато вкладок), система сама й поступово переносить
пам'ять старих, давно не активних програм на SSD — стільки, скільки потрібно, — замість того щоб
зависнути або вбити гру. Коли пам'ять звільняється, усе повертається без втрати даних.

## 1. Що є зараз (виміряно)

| Що | Стан |
|---|---|
| RAM | 15 ГБ |
| zram0 | 7.7 ГБ, zstd, пріоритет 100 (`/etc/systemd/zram-generator.conf`, ставить `mgos-zram setup`) |
| swap на SSD | **немає** |
| `vm.swappiness` / `page-cluster` | 150 / 0 (`/etc/sysctl.d/99-mgos-zram.conf`) |
| OOM-захист (systemd-oomd / earlyoom) | **вимкнено** |
| Диск | NVMe Samsung 512 ГБ, `/` на btrfs (`compress=zstd:3`, `subvol=@`), вільно ~82 ГБ |
| `mgos-pageout` | вручну витісняє пам'ять схованих з доку програм у swap (process_madvise) |

**Проблема:** zram живе в тій самій RAM. Коли RAM + zram заповнені, ядру нікуди скидати сторінки:
спершу все підвисає (ядро ганяє кеш файлів туди-сюди), потім спрацьовує OOM killer і може вбити саме гру.

## 2. Рішення (рекомендоване): zswap + swapfile на NVMe

Замість «zram окремо» — **zswap**: стиснений кеш у RAM *перед* swap на диску.
- Свіжі витіснені сторінки стискаються в RAM (як зараз у zram, так само швидко).
- Коли кеш заповнюється — **найстаріші** сторінки ядро саме пише на SSD (LRU). Це і є «давні програми
  на диск, скільки потрібно».
- Шринкер zswap (`zswap.shrinker_enabled`, ядро ≥ 6.8, у нас 6.18) під тиском пам'яті заздалегідь
  виносить холодні сторінки на диск, поки ще не пізно.
- Чому не «zram + swapfile з нижчим пріоритетом»: тоді zram забивається старими сторінками, а на диск
  ідуть *нові*, гарячі (інверсія LRU) → гра гальмує. zram writeback на диск теж є, але потребує окремого
  розділу/файлу-loop і ручних тригерів — складніше і крихкіше.

### Кроки

1. **Swapfile на btrfs** (на btrfs потрібен окремий subvolume без CoW/знімків):
   ```bash
   sudo mount -o subvolid=5 /dev/nvme0n1p4 /mnt
   sudo btrfs subvolume create /mnt/@swap && sudo umount /mnt
   sudo mkdir -p /swap
   # fstab: UUID=<root> /swap btrfs subvol=/@swap,noatime 0 0
   sudo mount /swap
   sudo btrfs filesystem mkswapfile --size 16g --uuid clear /swap/swapfile   # = RAM
   # fstab: /swap/swapfile none swap defaults,pri=10 0 0
   sudo swapon /swap/swapfile
   ```
   16 ГБ = обсяг RAM: вистачить на гру + фон. Займе 16 з 82 ГБ вільних.
   Якщо є snapper/timeshift — виключити `@swap` зі знімків.
2. **Вимкнути zram, увімкнути zswap** (параметри ядра в cmdline завантажувача + sysctl):
   ```
   zswap.enabled=1 zswap.compressor=zstd zswap.zpool=zsmalloc zswap.max_pool_percent=25 zswap.shrinker_enabled=1
   ```
   - прибрати `/etc/systemd/zram-generator.conf` (або `zram-size = 0`);
   - `vm.swappiness` 150 → **100** (диск повільніший за zram), `vm.page-cluster` 0 → **1**;
   - `vm.watermark_scale_factor = 125` — ядро починає звільняти пам'ять трохи раніше, без ривків.
3. **Захист від «трешингу» (MGLRU):** `echo 1000 > /sys/kernel/mm/lru_gen/min_ttl_ms` (через
   tmpfiles.d) — ядро не викидає робочий набір активної програми молодший за 1 с; якщо інакше не можна,
   спрацьовує OOM швидко, а не через 5 хв зависання.
4. **Останній рубіж — systemd-oomd** (замість ядерного OOM, що вбиває навмання):
   - `ManagedOOMMemoryPressure=kill`, `ManagedOOMMemoryPressureLimit=60%` для `user@.service`;
   - Hyprland, SYSui (topbar/dock/pixel_wallpaper), Pipewire — `ManagedOOMPreference=avoid`;
   - ігри (Steam, процеси з `gamemoderun`) — `avoid`; першими під удар — вкладки браузера / Electron.
   - Альтернатива без демона: лише кроки 1–3 (див. питання про kiosk нижче).
5. **«Режим гри» в mgOS:** коли стартує гра (Steam / gamemode / вікно на весь екран із класом гри) —
   один раз викликати `mgos-pageout --tree` для програм, схованих у доці, і для фонових важких
   (браузер, месенджери), щоб пам'ять звільнилась *до* того, як гра її попросить. Вже наявний
   `mgos-pageout` працює і з zswap — сторінки підуть у zswap, а холодні далі на SSD.
6. **Налаштування → Система → Пам'ять:** показ «у RAM / стиснено / на SSD» (з `/sys/kernel/debug/zswap`
   і `swapon --show`), перемикач «Режим гри», розмір swapfile. `mgos-zram` → перейменувати/розширити
   до `mgos-memory setup|status|json` (setup — кроки 1–4, ідемпотентно).
7. **Установщик + git:** `mgos-arch-install`/`install.sh` — створювати `@swap` і swapfile одразу;
   `sync_from_system.sh` — забирати fstab-рядки, sysctl, tmpfiles і юніти oomd.

## 3. Перевірка (до того, як казати «готово»)

- `stress-ng --vm 2 --vm-bytes 22G --timeout 120s` з відкритими Firefox + Telegram: система
  відповідає (курсор, док, перемикання вікон), `swapon --show` показує використання swapfile,
  OOM не вбив нічого з «avoid».
- Справжня гра на 10+ ГБ поверх браузера: FPS без провалів після першої хвилини; після виходу з гри
  браузер повертається з SSD за секунди.
- `cat /sys/kernel/debug/zswap/*` — пул заповнюється, `written_back_pages` зростає лише під тиском.
- Простій (нічого не відбувається): записів на SSD ≈ 0 (`iostat`/`/proc/diskstats`) — без зносу диска.
- **Kiosk-сесія:** вхід, батарея, жодних нових фонових процесів, поведінка як була.
- Відкат перевірений: `swapoff` + прибрати fstab/cmdline → повернення до zram без перевстановлення.

## 4. Ризики

- **Знос SSD:** пишемо лише під тиском пам'яті; NVMe на 512 ГБ має ресурс у сотні ТБ — swap у звичайному
  використанні це гігабайти на тиждень. Простій = нуль записів (перевіряється кроком вище).
- **btrfs:** swapfile лише в окремому subvolume без знімків, інакше `swapon` відмовить або знімок зламається.
- **Шифрування:** якщо колись буде LUKS — swapfile автоматично зашифрований разом із розділом.
- **Сплячий режим (hibernate):** не планується; якщо треба — swapfile ≥ RAM уже підходить, але це окремий план.

## 5. Відкриті питання до тебе

1. **Kiosk:** swap і параметри ядра — спільні для обох сесій. Варіант А — лише «пасивні» кроки 1–3
   (без демонів, у простої нуль витрат) для обох; oomd і «режим гри» — тільки в mgOS. Варіант Б — kiosk
   повністю як зараз (zram), а zswap+swapfile вмикається лише для mgOS — технічно складніше, бо zswap
   глобальний. Рекомендую А.
2. Розмір swapfile: 16 ГБ (= RAM) чи більше (наприклад 24 ГБ для дуже важких ігор)?
3. Чи вбивати щось автоматично взагалі (oomd), чи лише свопити і показувати сповіщення «мало пам'яті»?
